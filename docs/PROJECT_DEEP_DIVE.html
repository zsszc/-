01 / WHAT IT IS

项目定位与一句话边界

这是围绕跨境物流场景的 Agent + RAG + 业务工具 演示系统：问政策时查证据，问具体运单时用工具，证据不够时拒答，危险写操作先让人确认，后台能录知识、评测和复盘。

已实现

核心链路

意图识别、条件路由、知识检索/重排、证据闸、ReAct 工具循环、SSE 流式答复、会话持久化、后台评测入口。

已实现

演示场景

运单/时效与异常、清关与禁限寄、费用估算、理赔指引、转人工工单、知识库管理、问题归类与观测。

必须说明

不是生产物流平台

运单/费用使用项目内演示数据和规则，不代表承运商实时 API；前台传入的 user_id 未做强身份认证，不能称为生产级权限。

面试口径：说“完成一个可运行、可评测的物流 Agent 原型”，不要说“接入 DHL/UPS 实时运单”“具备企业级账号权限”“已经全量自动化无人工风险”。阿里云部署版本可能与本地不同；本手册描述当前本地仓库。

03 / PRODUCT

功能、页面与按钮到底做什么

页面 / 入口用户看到的事实际后端动作与注意点
/ 聊天提问、流式文字、引用、工具状态、运单/异常/报价快捷操作POST /api/chat 以 SSE 推 delta / citations / tool / actions / interrupt / done；非流式评测走 /api/agent。
/admin七张运营模块卡：运营概览、知识库、Agent 评测、RAG 评测、观测、飞轮审核、主题app/api/admin.py 聚合各模块状态；它是导航与状态概览，不是训练总控台。
/logistics-dashboard / /shipment-detail物流运营概览、能力与状态；单票运单详情读取项目内演示业务数据；不能说成外部承运商实时对接。
/kb语料来源、预览切块、去重、录入、向量化、搜索、自查预览不入库；录入先写 MySQL pending；向量化再写 Milvus 并标 done；搜索不等于回答质量通过。
/rag-eval传统检索指标、策略对比、忠实度案例报告来自评测脚本和复核表；“重跑”会更新报告，旧报告不是实时数值。
/agent-eval300 条 Agent 数据、分类通过率、在线评测任务在线跑会调用模型与工具，消耗费用；页面历史报告有时间口径。
/review低置信问题/差评后的待审核队列人工审核后才可回补知识；拒绝模型输出直接自动入库。
/observabilityLangfuse 链路、延迟/成本/质量趋势与校准信息Langfuse 配置可选；未启用时不能声称全链路 trace 可用。
/topics 与子页问题主题分布、按类钻取旁路分类/批处理，不替代主链路 LLM 意图识别；重训练不会自动改变 Agent 路由。旧版 ch10 作业还在注册表中，默认训练文件不是物流集，见第 11 节。
按钮理解公式：预览只算切块；录入库落业务表；向量化更新索引；重跑评测产生新报告；重训练更新旁路分类模型；审核通过才可让低置信问答进入可信知识生产路径。它们作用在不同层，不能互相替代。
04 / REQUEST

一条消息从浏览器到回复

  1. 前端提交：携带消息、演示 user_id、可选 conversation_id 访问 /api/chat。
  2. 会话入口：创建/读取 MySQL 会话，先记录用户消息；用会话 ID 作为 LangGraph thread_id；每轮重置 answer、证据、步骤计数等输出字段。
  3. 消解与识别：先用最近历史补全“它/这单”等指代，再做 LLM 意图识别；失败时有 JSON 和关键词降级。
  4. 分流：按投诉/闲聊/知识/售后/业务等出口进入不同节点；知识路必须检索，业务路可让 Agent 决定工具。
  5. 执行：知识路先检索和证据判定；业务路在 main_agent ↔ agent_tools 之间循环，步数上限由配置控制。
  6. 输出：Graph 事件映射为 SSE 增量文字、引用、工具、动作与中断；确认工单/选订单可用 Command(resume=...) 续跑。
  7. 留痕：持久化消息、摘要与工具审计；配置时记录 Langfuse trace；低置信问题进入待复核飞轮。
故障区分：聊天“回复失败”可能在模型 API、Milvus/MySQL、SSE 流、前端解析、MCP 或图节点任何一层。先看 HTTP 与 log/app.log，再看节点 trace。
05 / AGENT GRAPH

Agent 状态机：确定性外壳 + 有界 ReAct

清关/异常/理赔/一般禁限寄 → retrieve_knowledge → confidence_check

低于启发式阈值或自检认为证据不足，直接 fallback_reply；否则把编号证据注入本轮上下文，由 Agent 作答并引用。费用时效和明确物品寄运预检是例外，走业务工具路。

运单/费用/人工/具体禁限寄预检 → main_agent ⇄ agent_tools

模型提议工具调用，执行引擎校验参数、超时和审计，再把结果回灌。无 tool calls 或达到最大步数结束。ReAct 不等于无限自主执行。

售后 → fetch_order → retrieve_policy → main_agent

先取订单/可选订单，再查政策，最后让模型依据结构化订单和政策证据判断。部分步骤通过 interrupt 暂停；退款提交主要是前端表单入口，不能说成资金退款已完成。

投诉 / 闲聊 / 其他

投诉有确定性安抚/升级出口；闲聊和其他有脚本回复。确定性节点仍进入日志节点，不做无意义检索。

对应 app/graph/state.py、build.py、routing.py、nodes.py、runtime.py。messages 用 add_messages 合并；标量状态每轮显式清零。

06 / RAG

RAG 不只是“查向量”：入库、召回、重排、拒答

入库设计

data/kb/*.md → 按标题分节、递归切分、句子重叠/表格行处理 → 问答块/元数据 → 指纹查重 → MySQL knowledge_chunks pending → 批量嵌入 → Milvus 写索引 → done。

本轮新增 service-playbook.md 五个高频条目，产生 6 块；本地总计 25 块并完成向量化。内容是演示规则或带官方来源的通用提示，不是承运商价格承诺。

查询设计

问题标准化/同义扩展 → BM25 稀疏与 BGE-M3 稠密双路召回 → 融合、必要时子问题多路合并 → BGE reranker 二次排序 → 头尾重排 → 证据置信度 + LLM 语义自检。

“召回命中”不等于“可作答”：排序相关性只说明像，不说明足以支持结论；因此生成前再做证据闸。

证据分数为什么不能叫概率

score = 0.5 × top1 + 0.2 × min(valid_count / 3, 1) + 0.2 × margin + 0.1 × key_clause_hit
当前阈值 = 0.30；低于阈值拒答，高于阈值仍需 self-check。

四个信号是工程启发式加权，不是校准的“答对概率”。阈值应在独立评估集上做精确率/覆盖率取舍，不能只凭单个成功例子下结论。

本轮真实增量结果：先前四组高频题均为 0/5。补库后派送问题、地址修改、贸易单证各 5/5；账户权限因误路由修复后 3/5，合计 18/20。账户剩余两题仍保守拒答。20 条是定向回归，不可代替 300 条全量重跑或泛化结论。

外部依据：UPS Change a Delivery；DHL 商业发票指南。国家、线路、承运商适用条件仍需核对最新官方规则。

07 / TOOLS

工具、MCP 与“先确认再写入”

层当前职责面试解释要点
工具注册 registry.py扫描本地 builtin，发现 MCP 工具并统一成 ToolSpecMCP 是标准化工具发现/调用协议；本项目主要是本地物流/售后工具服务供 Agent 调用，不是“外部平台已接入”。
工具执行 engine.py校验参数、按来源执行、超时/重试、结果长度限制、审计日志模型只提议调用；执行由服务端裁决。不能把 prompt 当权限控制。
只读工具演示运单、SLA、费用、异常识别、禁限寄预检、FAQ 等结构化工具结果可当本轮证据，但仍应披露演示数据和规则的不确定性。
写工具/确认创建工单先校验、预览、interrupt，用户确认后 Command(resume)中断点前只做纯计算，避免恢复重跑造成双写。
退款入口检测订单归属后，submit_refund 转成前端表单动作这是引导提交，不是资金退款已完成。
模型产生 tool_call(name, args)
→ 根据 ToolSpec 校验 JSON 参数
→ 对缺失重量/不属本人订单做服务端拦截
→ 需要写入：先预览并 interrupt → 前端确认 → resume
→ 执行后记录 ToolMessage + 审计 → 回到 main_agent
→ 无 tool_calls / 步数封顶，结束
安全红线：user_id 来自请求体，当前没有真正的身份认证；演示级 owns_shipment/owns_order 只能展示归属校验思路。生产须引入认证、服务端主体绑定、授权、幂等键、速率限制、凭据管理与审计。
08 / CONVERSATION

会话状态、上下文三层与 SSE

持久与瞬时是两回事

MySQL 的 conversations/messages 保存业务会话；LangGraph AsyncSqliteSaver 保存图执行检查点，支持同一个 thread_id 的继续与人工确认后续跑。Graph 保留消息历史，但每轮 answer、evidence、steps、trace 等瞬时字段必须重置，否则上轮残留污染本轮。

三层上下文

层 1 最近原文；层 2 较旧消息半压缩；层 3 更旧内容进入会话摘要。summary_upto_msg_id 与 layer1_from_msg_id 是边界锚点。budget.compute() 为 system、工具、证据、输出和历史分别预留 token；最终用 trim_history 兜底。

模型消息只保留一条固定 SystemMessage，摘要和本轮检索证据跟在用户消息后。ReAct 后续步骤可复用稳定前缀；缓存命中要看上游 usage / 控制台，不能仅凭估算断言。

源码：app/graph/runtime.py、app/core/memory.py、app/core/budget.py、app/core/summarizer.py、app/api/chat.py。

09 / DATA

数据库、索引与最终一致性

存储主要对象为何存在 / 故障时怎么想
MySQLconversations、messages、tickets、knowledge_chunks、tool_audit_logs、review_queue、eval_runs、faith_cases、topic_classifications 等可查询的业务真相与审核状态；知识块 pending/done 可补偿。
Milvus知识块向量与稀疏/关键词检索索引负责相关性检索，不替代业务事务；能回链 MySQL 块 ID。
SQLite Checkpoint按 thread_id 的 LangGraph 执行快照支持跨轮状态和人工确认后恢复；不是业务消息主库。
报告文件评测、成本、训练等生成产物离线快照，不是在线实时观测；版本和时间都要核对。

双写为什么不直接开一个事务？

MySQL 事务管不到 Milvus 和外部嵌入 API。当前先写 pending，成功向量化/索引后置为 done；失败留下待处理项，后台再补偿。目标是可恢复的最终一致，不是跨系统原子事务。工程化扩展可加幂等键、outbox、重试退避、对账与死信队列；不能说当前全部具备。

高频知识补库本轮实测

data/kb/service-playbook.md 新增 5 个主题、6 个切块；预览重复 0，录入 6、跳过 0、成功向量化 6。本地 MySQL done=25/pending=0，Milvus 25；几个高频问法检索首位命中新增块。这些是本地结果，不等于阿里云已更新。

10 / EVALUATION

怎么评：检索指标与 Agent 行为必须分开

传统检索指标

30 条物流检索标注样本（19 单文档、11 多文档）比较 vector、BM25、hybrid、hybrid_rerank。Hit@k 看至少一条相关；Precision@k 看 Top-k 中相关占比；Recall@k 看相关集合覆盖；MRR@k 看首条相关排名；nDCG@k 看位置加权质量。

保存的一次 hybrid_rerank 快照：Hit@1=0.90、Recall@5=0.9611、MRR@5=0.9444、nDCG@5=0.9355。该报告生成于本轮补库前，30 题小样本，不可当新语料上线后的指标。

端到端 Agent 行为

300 条本地在线 v5：政策流程 100、跨文档 70、工具 60、库外拒答 50、边界澄清 20。脚本按类别检查证据标记、工具调用、拒答/澄清等行为；这不是人工事实正确率。

v5 基线完成 300/300、通过 210/300 = 70%。本轮仅 20 条定向复测 18/20；不能直接写“全量 300 提升到 90%”。

v5 300 条分类结果（补库前快照）

库外拒答43/50 · 86%
跨文档57/70 · 81.4%
边界澄清14/20 · 70%
工具操作38/60 · 63.3%
政策流程58/100 · 58%
严格解释：页面数字可能是特定子集/历史运行，不代表算法从未优化；要看报告生成时间、数据集版本、任务是否重跑。检索 Recall 高而端到端低，可能发生在意图误路由、证据闸拒绝、模型不引用、工具参数错误或评分规则过窄。

忠实度/幻觉评测是另一套人工/规则复核：答复是否有证据支撑、是否凭空扩展事实。仅输出“[1]”不等于忠实。

报告来源：data/evals/logistics_retrieval_eval_report.json（30 条旧快照）、本地运行产物 data/evals/logistics_agent_eval_report_live_v5.json（300 条基线）；评测逻辑 scripts/eval_logistics_retrieval.py 与 scripts/eval_logistics_agent.py。

11 / FEEDBACK

观测、成本、知识飞轮、旁路分类器

Langfuse 观测

runtime.init_graph() 在配置齐全时给图挂回调；同一会话标 session ID；记录模型/节点调用、延迟、token 与成本相关数据；用户反馈可回连会话。未配置时降级，不影响聊天核心，但不能虚构 trace 数据。

低置信知识飞轮

证据不足或差评 → 保留问题与召回快照 → 待审核 → 人工核对知识 → 录入/向量化 → 重新评测。最重要的是人工审核门：模型输出直接回灌会自我强化错误。

主题分类器的真实位置

旁路批处理和 topic_classifications 表支持主题分布；主聊天链路仍是 LLM 意图识别 + 确定性路由。训练脚本基于中文 RoBERTa-wwm-ext、17 类；单标签使用 softmax/argmax，多标签使用 sigmoid/BCE。MPS/CUDA/CPU 可运行，验证集 micro-F1 早停，最优权重暂存内存以减磁盘峰值。分类准确率不能替代 Agent 评测。

成本与缓存

关注每轮模型调用数、检索/重排次数、输入输出 token、工具结果体积、P50/P95 延迟、缓存读命中。上下文预算与固定前缀已在代码中；省钱比例需要真实对照。

深挖出的训练入口陷阱：make ch10-train 默认调用 scripts/ch10/train.py；该脚本若发现 data/ch10/dataset/train.jsonl 就优先读取它，而仓库中这个文件第一条是旧电商“价保”问法（共 2593 条），不是物流 300 条训练集。物流 v2 文件另有 logistics_train_v2.jsonl（300）、logistics_val_v2.jsonl（51）、logistics_test_v2.jsonl（170）。因此不要在后台把默认“全参微调训练”按钮解释为“自动训练物流分类器”；要跑物流实验需显式给 --train-file、--val-file 和独立输出目录，并先核对标签模式。此次没有触发重训练。

对应 app/core/observability.py、app/api/observability.py、app/kb/mining.py、app/api/review.py、scripts/ch10/train.py、app/api/topics.py。

  1. 问“德国清关需要什么资料”，展示引用证据与条件边界。

  5. 打开 KB 页面说明预览、查重、录入与向量化的不同；避免重复录入已有语料。
  6. 打开 Agent/RAG 评测，主动指出 70% 基线、弱项和 20 条定向回归。

13 / STORY

把项目讲给面试官：30 秒、2 分钟、5 分钟

30 秒开场

“我做了一个跨境物流场景的 Agent 原型。提问进入 FastAPI 和 LangGraph，知识问题强制走混合检索与证据闸，运单/费用走业务工具。系统有会话记忆、SSE、人工确认、知识库管理和评测。我重点解决的是‘查得到但答不准’与‘没证据还乱答’。”

2 分钟结构

场景与约束 → 路由架构（LLM 意图 + 确定性 Graph）→ RAG（BM25/向量/重排 + 双闸）→ 工具/MCP 与确认 → 真实结果（300 条 70%，高频定向 18/20）→ 不足（权限、演示数据、小样本波动）。

5 分钟深入

选一条失败样本复盘：账户权限 FAQ 被“运单”误导到业务路；补语料仍失败；加窄规则后 5 条从 0 到 3，剩两条自检拒答。说明你能跨数据→路由→证据→生成→评测定位，而不只调 prompt。

简历写法：“构建 FastAPI/LangGraph 跨境物流 Agent 原型，集成混合检索与重排、证据门控、MCP/内置工具、SSE 会话与可中断工单；建立 300 条分层行为评测与 30 条检索标注集，在线基线 210/300，定向知识补库与误路由修复使 20 条高频回归通过 18 条。”数字要附版本口径，不写成线上大盘 KPI。
